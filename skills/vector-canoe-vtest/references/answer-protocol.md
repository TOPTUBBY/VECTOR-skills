# Function-answer verification protocol

Use this for CAPL functions, types, event procedures, vTESTstudio commands, and version-sensitive GUI instructions. The public skill is a workflow and original synthesis; the private corpus is a searchable copy of a user's authorized local Help, not an independently validated API.

1. Identify the exact product, version/service pack, bus technology, CAPL program placement (Simulation Setup, Measurement Setup, test module/unit), and the requested operation. `msTimer` is a type, while `setTimer` is a function and `on timer` is an event procedure.
2. Run `local_corpus.py card --db <private-db> <exact-name> --product <label>` and `lookup --full` for the selected topic. If exact lookup fails, `search` related terms, spelling and bus namespace. Read all relevant overloads and linked topics. Check `stats` for extraction omissions. A parsed card can omit a section or mistake a cross-reference for an example.
3. For migrations run `compare` across the locally available versions, then inspect the full matching topic in each product. Equal extracted signatures do not establish identical behavior. Check vTESTstudio's own release notes/Concept Manual and CANoe runtime compatibility when a test unit is involved.
4. Check an independent **official** source for the claimed version: installed Help in its original viewer, Vector online Help/KnowledgeBase, official release notes or compatibility matrix. Compare spelling/case, parameter order and types, return/error meaning, event restrictions, bus and options, version availability, and side effects. For a recent version, consult its current Help rather than projecting CANoe 14 behavior forward. If online Help is blocked, say so and mark the online check pending; do not imply it succeeded. Other web material may suggest search terms but does not supersede the matching primary documentation.
5. Give the exact signature only when the relevant topic supports it. Explain each parameter and return value in your own words, with an original small example appropriate to the specified context. Label uncompiled examples as illustrative. If a local compiler/runtime is available, validate the code and report the version and result. Include the local topic path and official URL or document title/date used for the cross-check. Surface conflicts explicitly, with each source's version.

Suggested compact answer: **Applies to** product/SP/context; **Syntax** and parameter/return table; **How it works** and a short example; **Version and context caveats**; **Verification** (local topic, independent official source, compiler result or reason pending). Do not paste a whole Help page into an answer or public issue.

For a standalone Gemini Gem, the local SQLite corpus is unavailable unless the user supplies an authorized excerpt. Use accessible official sources and the original reference files; disclose that absence instead of inventing a local verification.
